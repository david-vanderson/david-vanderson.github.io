Layout: Expand but Don’t Scroll

A layout situation:

  • floatingWindow with scrollArea
  • few labels/controls at the top
  • the rest is a grid

We want both of these properties:

  • grid takes up all remaining space in the floatingWindow
  • grid does NOT cause floatingWindow scrollArea to scroll
    • if needed, grid should scroll internally

Solution:

  • grid .expand = .vertical
    • take all remaining space
  • grid .max_size_content = .height(100)
    • tell scrollArea we only need 100 pixels, so it won’t scroll (unless very tiny)

This works because of how .max_size_content and .expand interact. min_size_content is not the minimum and max_size_content is not the maximum.

I’m calling out this specific layout case and solution. I spent far too much time figuring out what dvui change was needed until realizing we supported it out of the box.

New keybinds for cmd/ctrl-plus/minus that adjust the content scale, similar to a browser tab.

  • dvui.App turns it on by default
  • web forces it off (because browser does it)

The intention is to help people who would use a screen magnifier. This gives an alternate way to increase the content size of an application where most drawing is still sharp.

Inspired by Trevor Settles lighting talk “I Just Wanted a Non-Blurry Screen Magnifier” at Software Should Work 2026

Grid Column Sizing

Paul Hatchman put a lot of work into helping me sort out how grid columns should work. We now have 3 categories:

  • normal
    • column does not take extra space
    • width is determined by min width of all run cells (and colHeader)
    • resizing changes this column’s width only (other expanded columns might adjust)
  • expanded
    • when at least one cell (or colHeader) has .expand = .horziontal or .both
    • takes extra space weighted by min width
    • resizing makes an offsetting change in other expanded columns (or normal if needed)
  • fixed
    • .resizable = false passed to colHeader
    • turns off user drag-resizing
    • won’t be changed when other columns resize

When the grid does not have enough horizontal space (and no horizontal scrolling), fixed get all their space, normal/expanded are shrunk weighted by min width.

Please ask or file an issue if you are having trouble with grid!

Text Layout Long Lines

Colton Franklin provided an initial implementation and helped fix long line performance in textLayout/textEntry (when using .cache_layout = true).

Now when a line of text is many times as wide as the visible width, textLayout can skip non-visible portions of the line.

While most of the changes are internal, the api needed to change to communicate which spans of bytes were going to be visible. This allows callers to skip expensive calculations (like syntax highlighting) for bytes that textLayout is going to ignore anyway.

The new api is to call cacheLayoutNext() in a loop:

  • each call returns the “current” visible region (start and end bytes)
  • once textLayout has seen enough bytes to get to the end, cacheLayoutNext() will advance to the next region

Here’s the code that textEntry uses when syntax highlighting:

outer: while (true) {
    const cln = self.textLayout.cacheLayoutNext();
    iter.setByteRange(cln.start, cln.end); // bytes range we want highlighted
    while (iter.next()) |h| {
        self.textLayout.addText(h.text, h.opts orelse normal_opts);
        if (self.textLayout.bytes_seen >= cln.end) continue :outer; // need next byte range
    } else {
        break :outer; // ran out of text
    }
}

self.textLayout.addTextDone(normal_opts);

One unanswered question is how the api should work for an application that is retrieving the contents dynamically (like from a database). Currently we don’t have a way to tell textLayout to pretend we gave it a bunch of bytes.

If you are in that situation please file an issue!

Fancy Corners

Big thanks to Logickin for overhauling our corner drawing.

Previously corners were assumed to be circles with a custom radius.

Now you can individually specify each corner with options:

  • square - sharp corner
  • round - circle with custom radius
  • chamfer - 45 deg cut with custom size
  • angular - angle cut with custom x/y offset
  • nudge - adjust where the corner is drawn (makes things like trapezoids possible)
  • default - use corner style and size from theme
  • theme - use corner style from theme with custom size

Options.corner_radius is replaced by Options.corners.

Theme.max_default_corner_radius is replaced by Theme.corner.

New builtin “Tech” themes show what you can do. Check it out!

Time Tracking

secondsSinceLastFrame now reports a reasonable default value (10ms) if the underlying clock goes backwards.

dvui tries hard to compensate for a clock jumping backwards. frameTimeNS will not go backward, which makes it decent to use for performance numbers.

For general UI timing stuff (like tracking how long a key has been pressed), secondsSinceLastFrame is good because it will always report a value greater than 0 and less than ~71.5 minutes (2^32 micros). If the clock jumps back, it will report 10ms.

That means your UI (including dvui animations) will continue to work reasonably well even if the clock goes wrong.

Texture UV Rect and Wrapping

Textures gained options for whether to clamp or repeat uv values.

renderTexture got a .uv_rect option that specifies a screen rectangle that logically covers the .uv coords given. This can make showing part of a larger texture more intuitive.

Mouse Type

Building on last month’s scrolling heuristic, you can now use dvui.mouseType to see which kind of mouse (touchpad vs. wheel mouse) dvui thinks the user is using.

This can be useful in situations where you want a mouse wheel to work differently than two finger touchpad scrolling (like zooming vs. panning).

The heuristic is based on the values dvui sees from mouse wheel events. Please report problems!

The tab index of a widget controls its keyboard navigation focus order. These used to be global inside each subwindow.

RenderFrontToBack

New utility for overlapping widgets to change the rendering order.

The problem is the first widget processes events first, but will be painted over by later widgets. This results in events going to the widget that is visually behind other widgets.

RenderFrontToBack is a new helper that collects rendering and defers it so that if all the overlapping widgets use it, the first widget to run will be painted last. Events will now be handled by the widget visually in the front.

It’s used in the demo “Scroll Canvas” section.

March 25, 2026

Box Layout

BoxWidget (dvui.box) is used to layout a single line of widgets vertically or horizontally. It is also used for general spacing/positioning.

Children with normal layout are split into 2 categories:

1. Packed (gravity is 0 or 1)

A child with gravity (in the box direction) of 0 or 1 is “packed”. All packed children are lined up in the box direction.

The box’s min size is the sum of the packed min sizes in the box direction.

If the box has extra space, it is allocated equally among all packed children that are expanded in the box direction. Setting .equal_space = true means the total box space is divided among all packed children.

Tip: use gravity of 1 to pack the box “at the far end”. This is a good way to swap the order of widgets without having to change the execution order.

2. Unpacked (gravity between 0 and 1)

A child with gravity (in the box direction) between 0 and 1 is “unpacked”. These are positioned within box’s contentRect without regard to any other children in the box.

This is useful to position a single child inside a larger box.

Boxes rarely have both packed and unpacked children.

March 24, 2026

Layout

Layout of dvui widgets comes in 3 flavors.

1. Parent Decides - normal layout

This is the most common. The parent uses the child’s Options:

  • min_size_content (padding/border/margin are added automatically)
  • gravity_x/y
  • expand

And gives the child a Rect inside the parent’s contentRect. The Rect is entirely up to the parent widget. See Box Layout.

A widget’s Rect includes its content rect, padding, border, and margin.

Tip: negative margins can be used to overlap sibling widgets, usually to “collapse” a duplicated border.

Advanced Tip: a child can adjust its Rect by calling .data().rectSet(). This is how the wiggle button works, and is invisible to the parent.

A non-expanded parent is always tightly packed around its normal children (using their min sizes). Options.max_size_content clamps how big this packing can get. Especially useful for constraining textLayout, textEntry, and flexBox.

Tip: textLayout, textEntry, and flexBox adjust their height according to their width. Min width is calculated assuming no line breaking. Min height is calculated based on the current width.

Note that a widget can expand past max_size_content. See min_size_content is not the minimum

Tip: when drawing a dynamic element (like a progress bar), don’t size the element with .min_size_content, because that can affect its parent’s min size. Instead size a container, and directly draw the dynamic element (using Rect.fill or Path.stroke).

2. Child Decides - passes .rect in Options

This is used for situations like the “scroll canvas” demo, where children know their own position. It’s also used in infinite scrolling situations like the icon browser.

Children that pass .rect are invisible to their parent, but still use the parent’s contentRect as coordinates.

If expanded, the child’s Rect size in the expanded direction will be the parent’s contentRect size.

If the .rect passed has zero width/height, it will use the child’s min width/height.

Advanced Tip: if you have overlapping widgets (like in the scroll canvas demo) use dvui.RenderFrontToBack so events will be processed by the widget visually on top.

3. Child Floating - uses a Floating...Widget

The floating widgets (FloatingMenuWidget, FloatingTooltipWidget, FloatingWidget, and FloatingWindowWidget) use strategy 2 and pass .rect to opt out of normal layout.

In addition they create new subwindows, which operate as separate layers:

  • subwindows have a stacking order
  • drawing is defered to respect the stacking order
  • each subwindow has its own focused widget and keyboard navigation order

Use one of the floating widgets to show content that logically pops above and separate.

Examples include:

  • dialogs
  • menus, tooltips, and dropdowns
  • things being dragged
  • touch editing text

Texture Targets

Some texture target improvements:

  • dvui.Texture.Target.clear() clears to fully transparent
  • dvui.Texture.Target.destroyLater() destroys at end of frame
  • dvui.Texture.fromTargetTemp() gets a temporary (dvui-owned) texture from a target that can be drawn

These give more control to applications that want to reuse a target texture.

Most backends treat textures and target textures fairly interchangeably, but not all. To deal with this, we are trying out having two functions to get a normal texture from a target:

  • .fromTarget() destroys the target texture
    • user code is owns and must destroying the returned texture
  • .fromTargetTemp() leaves the target texture alone
    • returned texture is temporary (good for this frame only)

Retaining Textures and Data

dvui implements a form of garbage collection for textures and data. If you don’t reference a texture or call dataGet/Set for a frame, we free that memory. But sometimes you want to keep things around a bit longer.

Now we provide functions textureRetain, dataRetain, and retainClear.

These give a way to keep dvui from freeing these things, while associating them with a “retain key”. That key can be passed later to retainClear to tell dvui to stop retaining them.

This was motivated by the demo’s stuttering when reshowing the demo buttons (which trigger regenerating a bunch of textures). It’s now fixed by:

  • retaining the generated textures and associated data
  • the retain key is the demo window id
  • the demo window has a placeholder data with dataSetDeinitFunction which calls retainClear

So the flow is:

  • while the demo window is shown, we retain the textures/data
  • when the demo window is closed, we free the placeholder data
  • the deinit function calls retainClear
  • the textures/data are freed

These features all come together to allow retaining data to match the lifetime of some higher level widget.

Fonts

Font selection got a major upgrade. Until now we had to refer to an individual font ttf.

Now Font acts like a query that searches for a matching Font.Source:

  • .font = .theme(.heading)
  • .font = Font.theme(.heading).larger(2)
  • .font = dvui.themeGet().font_mono.withWeight(.bold).withStyle(.italic)

dvui.Theme has 4 fonts (body, heading, title, mono) and grew an embedded_fonts field so that font sources can be tied to the theme that requires them.

For now we still only have a single pool of Font.Source that is internal to dvui. In the future we hope to extend this to be able to query for system fonts.
